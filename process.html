How PASTEL designs training, and one worked example

Every PASTEL project follows the same seven steps. The Invoice case file below shows the steps applied to a portfolio module, including what a design review found wrong with version 1 and what changed in version 2.

Read this first. The scenario is fictional and the module uses fictional data. The case file reconstructs the design reasoning behind a portfolio piece, and no real learners or organizations are involved. The evaluation section is a plan, not a set of results.

Case files: Invoice simulator · Compliance simulator · API onboarding simulator

The standard process

01Define the performance problem

What should people do differently, and is training the right fix? Compare desired and actual performance, then screen the causes: missing knowledge or skill, poor tools, weak incentives, or process barriers.

Frameworks: performance gap analysis (Mager & Pipe), Human Performance Technology, Action Mapping (Cathy Moore).

Decision rule: if the cause is tools, incentives or process, say so. Don’t build training for it.

02Analyze the task

Break the job into the decisions people make and the cues they use to make them. Note where experts and novices differ, and where novices are likely to go wrong.

Frameworks: Cognitive Task Analysis.

Decision rule: design practice around decisions, not topics.

03Profile the learners

Record prior knowledge, work context and available time. Support that helps beginners can slow experts down, so scaffolding has to fade as skill grows.

Frameworks: expertise reversal effect (Kalyuga), cognitive load theory.

Decision rule: state the assumed starting point, then test it with real learners.

04Set objectives and assessment first

Write observable objectives, then the assessment items that would prove them, before drafting any content.

Frameworks: instructional alignment, criterion-referenced assessment (Dick & Carey tradition).

Decision rule: if an activity doesn’t serve an objective, cut it.

05Design practice and scaffolds

Reduce wasted mental effort, for example by placing related information together. Use worked examples early and fade them. Keep the practice close to the real task.

Frameworks: cognitive load theory (Sweller), split-attention and worked-example effects, Merrill’s First Principles, Gagné’s events of instruction.

Decision rule: put the information next to where it’s used.

06Build, instrument and test early

Prototype quickly and run formative evaluation: expert review, one-to-one tryouts, then a small group. Capture event data so later evaluation has something to use.

Frameworks: rapid prototyping, formative evaluation, xAPI.

Decision rule: test with a few real users before polishing anything.

07Evaluate at four levels

Plan Reaction, Learning, Behavior and Results measures at the start. Levels 3 and 4 need workplace data, so the metric, the baseline and the data owner must be agreed before launch.

Frameworks: Kirkpatrick Four Levels, with confirmative follow-up months later.

Decision rule: name the metric, the baseline and the owner before launch.

Case file: Enterprise Invoice 3-Way Match Simulator

Launch v2Open archived v1

1. Performance problem (fictional scenario)

An accounts payable team relies on a 60-page ERP manual. New specialists are expected to apply three rules when matching an invoice to its purchase order and goods receipt, but the rules are buried in the manual. Desired performance: apply the rules the same way every time. Non-training causes to check first: whether the ERP displays variance clearly, and who owns the tolerance policy.

2. Task analysis

StepDecision and cuePredicted novice error
1. Compare quantities across PO, receipt and invoiceDoes invoice quantity exceed receipt quantity?Trusting a matching invoice total and missing a receiving shortfall
2. Work out the price or FX varianceIs the absolute variance within 0.50%?Misjudging values at or near the limit
3. Choose a dispositionApprove, hold for Procurement, or rejectOver-escalating small variances, or approving above tolerance

The errors are predicted from the task, not observed in real learners.

3. Learner profile (assumed)

A new accounts payable specialist who knows basic accounting terms, works in an ERP system, and has not yet learned this company’s tolerance policy. These assumptions would be checked in one-to-one tryouts before any wider release.

4. Objectives and assessment

ObjectiveAssessed by (v2 cases)
O1. Spot a receiving shortfall even when the totals matchINV-2026-892, INV-2026-921
O2. Judge a variance against the 0.50% tolerance, including values at the limitINV-2026-884, 889, 901, 907
O3. Choose the correct disposition and apply the checks in orderAll six cases

5. Design decisions in v1

DecisionPrincipleHow it shows up
PO, receipt and invoice shown side by sideSplit-attention effectOne ledger table, so learners don’t flip between documents
Rules shown beside the dataInformation at the point of useAn embedded job aid instead of a manual lookup
One decision per caseChunkingA queue of short cases
Specific feedback for each wrong choiceCorrective feedbackEach wrong option explains what was missed

6. Build and instrument

HTML and JavaScript in a single page, with no server. v1 showed an activity log labeled as an xAPI stream. v2 builds real xAPI-structured statements in the browser and offers them as a JSON download.

7. Evaluation plan (Kirkpatrick)

LevelQuestionInstrumentData ownerSuggested timing
1 ReactionWas it clear and relevant?Short rating survey after completionLearnerImmediately
2 LearningCan they apply the rules to unseen cases?First-attempt score on a fresh case set, compared before and afterL&DImmediately and after two weeks

4 ResultsDid outcomes move?Exception error rate, rework and escalation volume, late-payment incidents, each against a baseline set before launchFinance operationsQuarterly

Because the scenario is fictional there are no baselines, so no results are shown.

8. Design review: v1 to v2

Issue found in v1Why it mattersChange in v2
Answer options described the rule that made them correctLearners could match wording instead of applying the rulesOptions describe the action only
Correct answers always came in the same orderA pattern could be guessedCase order and option order are shuffled

Case file: KYB / AML Compliance Decision Simulator

The policy, the entities and the escalation rules in this module are fictional. Real AML procedures vary by institution and jurisdiction, and this is not compliance training for real use.
Launch v2Open archived v1

1. Performance problem (fictional scenario)

New onboarding analysts at a fictional fintech are expected to match their response to the level of risk in a business customer’s file. Desired performance: approve clean files, ask for documents when an item can be explained, and escalate serious indicators without acting alone. Non-training causes to check first: whether the escalation policy is written down and findable, and whether the case system shows ownership and activity data together.

2. Task analysis

StepDecision and cuePredicted novice error
1. Check ownership transparencyCan the beneficial owner be identified?Accepting a registry entry without asking who actually controls the entity
2. Compare activity with the expected profileDoes the volume and pattern match?Treating any mismatch as wrongdoing, or ignoring it
3. Screen for PEP exposureIs there a match, and is it explained?Reacting to any PEP link the same way, or missing opacity combined with a PEP link
4. Choose a proportionate responseApprove, request information, monitor, or escalateOver-escalating clean files, or acting alone on serious indicators
5. Decide again when new information arrivesDo the documents resolve the open items?Anchoring on the first impression

The errors are predicted from the task, not observed in real learners.

3. Learner profile (assumed)

A new onboarding analyst who knows the basic terms (beneficial owner, PEP) but has not yet learned this firm’s escalation policy. These assumptions would be checked in one-to-one tryouts.

4. Objectives and assessment

ObjectiveAssessed by (v2 cases)
O1. Tell a clean profile from one with open itemsCASE-101, and the first decision in CASE-112
O2. Choose a proportionate first responseThe first decision in every case
O3. Decide again when new information arrivesThe second decision in CASE-104 and CASE-112
O4. Recognize patterns that call for immediate escalation without contacting the clientCASE-109

5. Design decisions in v1

DecisionPrincipleHow it shows up
Dossier beside the decision panelSplit-attention effectFacts and choices on one screen
Three tiers of responseProportionality as the core conceptApprove, enhanced due diligence, block
Short case queueChunkingOne entity at a time
Feedback that names the consequenceCorrective feedbackEach wrong choice explains the risk

6. Build and instrument

HTML and JavaScript in a single page. v1 showed an activity log labeled as an xAPI stream. v2 builds xAPI-structured statements for each decision in the browser, with a JSON download. Nothing is sent to a learning record store.

7. Evaluation plan (Kirkpatrick)

LevelQuestionInstrumentData ownerSuggested timing
1 ReactionWas it clear and relevant?Short rating surveyLearnerImmediately
2 LearningCan they choose a proportionate response on unseen cases?First-attempt score across decisions on a fresh case setL&DImmediately and after two weeks
3 BehaviorDo real decisions follow the policy?Quality review of a sample of real onboarding decisions: proportionality and timeliness of escalationCompliance QA30 to 60 days
4 ResultsDid outcomes move?Unnecessary escalations, time to decision, quality-review findings, each against a pre-launch baselineCompliance operationsQuarterly

Because the scenario is fictional there are no baselines, so no results are shown.

8. Design review: v1 to v2

Issue found in v1Why it mattersChange in v2
Each dossier carried a risk label such as “HIGH RISK” or “CRITICAL”Learners could read the label instead of weighing the evidenceLabels removed; the learner reasons from the facts
Described as branching, but it was three independent single choicesThe description promised more than the design deliveredDescribed accurately; two cases now present a second decision when new information arrives
Described as decided “under time constraints,” but nothing was timedThe claim was untrueClaim removed. Speed pressure is a later fluency goal, and would add load for novices
Option text stated the criteria (“illicit activity markers detected”)Learners could match wording instead of judgingOption text describes the action only
Answers always came in the same orderA pattern could be guessedCase order and option order are shuffled
“Block account and file SAR” offered as an analyst actionAnalysts normally escalate, and the officer decides on reports and freezesReplaced with escalation to the compliance officer. A practitioner should review this rule
“100% Analytical Accuracy” and “LRS CONNECTED” labelsThe record and the label overstated what happenedFirst-attempt scoring and statements labeled as generated locally
Feedback not announced to screen readersLearners using assistive technology missed the resultLive region, and smooth scrolling respects reduced-motion settings

Still not done: v2 has not been tested with real learners, a full accessibility audit has not been run, and the policy has not been reviewed by an AML professional.

Case file: Crypto Payment Webhook Onboarding

The API, keys, secret and signing scheme in this module are fictional. The signing scheme is a simplified teaching version, so real providers differ and nothing here should be copied into production.
Launch v2Open archived v1

1. Performance problem (fictional scenario)

A fictional payments company finds that some integrators ship webhook handlers that skip signature checks or accept old requests. Desired performance: integrators authenticate correctly, handle the right event types, and verify both the signature and the timestamp before crediting funds. Non-training causes to check first: whether the SDK offers a verification helper, whether the documentation buries the signing rules, and whether the sandbox ever sends a bad signature. If the SDK did the check by default, training would matter much less.

2. Task analysis

StepDecision and cuePredicted novice error
1. Authenticate the requestWhich header and scheme does the reference specify?Using a familiar scheme instead of reading the reference
2. Pick the event typeWhat state is the transfer in?Confusing pending and completed events
3. Verify the signatureDoes the expected signature match the received one?Skipping the check, or comparing the wrong body
4. Check the timestampIs the request within 5 minutes of its timestamp?Treating a valid signature as proof the request is fresh

The errors are predicted from the task, not observed in real learners.

3. Learner profile (assumed)

A developer who is comfortable with JSON and HTTP basics but new to this API and to webhook signature verification. These assumptions would be checked in one-to-one tryouts.

4. Objectives and assessment

ObjectiveAssessed by (v2)
O1. Build the authentication header the reference specifiesStep 1
O2. Choose the event type that matches a scenarioStep 2
O3. Detect a body altered after signingStep 3, request with the changed amount
O4. Reject a validly signed but stale requestStep 3, request that arrives 15 minutes late
O5. Accept a valid, fresh request without over-rejectingStep 3, the valid request

5. Design decisions in v1

DecisionPrincipleHow it shows up
Authentication taught before payloadsSegmenting to limit split attentionOne concept per step
Live request preview beside the taskImmediate representation of consequencesThe inspector updates as the learner chooses
Three steps with shrinking supportFading scaffoldsLabeled worked example, faded prompt, then independent
HTTP-style feedbackAuthentic contextStatus codes in the inspector

6. Build and instrument

HTML and JavaScript in one page. v2 computes real HMAC-SHA256 signatures in the browser using the built-in Web Crypto API, and builds xAPI-structured statements for each decision, with a JSON download. Nothing is sent to a learning record store.

3 BehaviorDo their handlers verify signatures and timestamps?Review of integrators’ sandbox traffic and code samples against a checklistIntegration support30 to 60 days
4 ResultsDid outcomes move?Rejected-forgery tests passed, integration support tickets, time to first successful integration, each against a pre-launch baselineDeveloper relationsQuarterly
